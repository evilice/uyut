# 6. Мёртвый код в `main.js` и `index.html`

**Статус:** не сделано · **Риск:** низкий · **Объём:** ~20 строк

## Постановка

Три находки, каждая подтверждена grep'ом по текущим файлам.

### 6.1 Недостижимая ветка ответа сервера (важнейшая из трёх)

`main.js:59` читает ключ `stored` из ответа:

```js
if(result.stored){ success.querySelector('h3').textContent='Заявка сохранена'; ... }
```

Но `send.php:12` формирует ответ фиксированной формой и ключа `stored` не содержит:

```php
echo json_encode(['success' => $success, 'message' => $message], JSON_UNESCAPED_UNICODE);
```

`grep -c stored send.php` = 0. Ветка не выполняется **никогда**.

Из этого следует содержательная проблема, а не только мёртвый код: при отказе почты
(`send.php:145`, `$sent === false`) сервер отвечает `503` и заявка **теряется** — ни в
почту, ни на сервер. Обещание «заявка сохранена, но письмо не отправлено» в интерфейсе
есть, а реализации нет.

### 6.2 Неиспользуемая переменная

`main.js:2` — `const regularPaintingImage = (workshops.find(w => w.title === 'Регулярные занятия...`
объявлена и не читается нигде (1 вхождение, 0 использований). Осталась от версии, где
картинка курса подставлялась отдельно; сейчас курс рендерится карточкой из `workshops.push`.

### 6.3 Мёртвые hidden-поля формы

В форме заявки есть `<input name="_subject">` и `<input name="_template">` (по 1 вхождению).
`grep -c '_subject\|_template' send.php` = 0 — сервер их не читает, тема формируется
на сервере (`$encodedSubject`, строка 145). Наследие Formspree, через который заявки
ходили раньше.

## План реализации

1. **Решить 6.1 с владельцем** — два равноправных варианта:
   - **(A) сделать ветку реальностью:** при `$sent === false` записывать заявку в файл
     вне web-рута (например `../uyut-spool/YYYY-MM.jsonl`, недоступный по HTTP) и отвечать
     `{'success':true,'stored':true,...}`. Заявки не теряются, но нужен путь вне docroot
     и решение, кто и как читает этот журнал.
   - **(B) удалить ветку** из `main.js` и оставить честную 503 с текстом «позвоните».
     Дешевле, но каждая неудачная заявка потеряна безвозвратно.
   Для локального бизнеса, где каждый лид на счету, разумно (A) — но это изменение
   `send.php`, а не только JS, поэтому нужно явное решение.
2. **6.2** — удалить объявление `regularPaintingImage`.
3. **6.3** — удалить `_subject` и `_template` из формы; убедиться, что `send.php` не
   строит тему из posted-значения (проверить `$encodedSubject`), иначе сначала перенести
   тему на сервер явно.
4. Прогнать `node --check assets/js/main.js` и регресс-набор диалогов + тест отправки
   с подменённым `fetch` (успех / 503 / сеть-не-доступна), чтобы ветки ответа не разошлись.

## Критерии приёмки

- `grep -c regularPaintingImage assets/js/main.js` = 0.
- `grep -c '_subject' index.html` = 0 и заявка уходит с корректной темой письма.
- Выбранная ветка 6.1 работает и проверена: для (A) — имитация `mail()===false` даёт
  `stored:true` и строку в журнале; для (B) — интерфейс обещает «сохранена» только когда
  это правда.
- `result.stored` в JS соответствует реальному контракту ответа.

## Риски

Низкие, кроме (A): появление файла-журнала заявок на хостинге — это персональные данные,
нужны корректные права доступа, размещение **вне** docroot и политика хранения
(согласно `privacy.html` / согласию на обработку ПД).
