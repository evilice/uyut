# 10. Правила аудита верстки и дизайна

**Статус:** введено 22.11.2026, переработано 22.11.2026 · **Область:** все публичные
страницы: `index.html`, `privacy.html`, `consent.html`, `user-agreement.html` ·
**Связанные документы:** [`09-design-audit.md`](09-design-audit.md) — исторический
список доработок, [`07-css-conflicts.md`](07-css-conflicts.md) — правила CSS,
[`README.md`](README.md) — правила сопровождения проекта.

**Авторитет документа.** Это единственный источник порогов и важности. Если `09`,
`07` или `README` расходятся с этим документом, действует `10`. `09` — снимок
текущего долга и применение правил, а не второй стандарт.

## Зачем этот документ

Чтобы аудит не зависел от вкуса и настроения проверяющего. Любое замечание должно
ссылаться на ID правила из §4, иметь измерение и проверяемый критерий готовности.
Одинаковые проблемы на разных страницах должны получать одинаковую важность, а
«мне не нравится» — не попадать в список дефектов.

Документ отвечает на три вопроса:

1. **Что считается дефектом**, а что — вкусовым решением.
2. **Как определить важность** (Обязательно / Важно / Желательно / Рекомендация).
3. **Как проверить** каждое правило и что считать исправленным.

## 0. Как пользоваться

1. **Нормативен только §4.** Если правила нет в реестре, это не дефект, а
   рекомендация. Правила с важностью «Рекомендация» в приёмку не входят.
2. **Правила применяются к новым и изменяемым элементам.** Известный долг из §10
   не переоценивается на каждом аудите: он закрывается по плану `09`. Новый код
   не должен увеличивать долг.
3. **Один пункт — одна проблема.** Нельзя объединять «поправить отступы и
   переписать тексты»: у них разные критерии готовности.
4. **Осознанное исключение** фиксируется в §5. Без записи в §5 нарушение остаётся
   дефектом, даже если оно «так задумано».
5. **Ссылка на ID обязательна.** В замечании указываются ID правила, селектор,
   ширина, измерение и критерий из §7.

## 1. Источники и целевой уровень

| Источник | Что берём | Статус |
|---|---|---|
| **WCAG 2.2, уровень AA** | контраст 4.5/3.0, non-text 3:1, не только цвет, autocomplete, фокус, target size 24px, reflow 320px, статус-сообщения, ошибки формы, text spacing, images of text | обязательный минимум |
| **WCAG 2.5.5 (AAA)** | target size 44×44 | внутренняя цель для основных touch-действий |
| **WCAG 2.3.3 (AAA)** | reduced motion | внутренняя цель |
| **W3C HTML / CSS, MDN, ARIA APG** | семантика, landmarks, диалоги, имена кнопок, `aria-*` по назначению | обязательный минимум |
| **Apple HIG / Material Design** | 44–48px зоны нажатия, паттерны мобильного меню и модалок | рекомендация |
| **Русская типографика** | кавычки-ёлочки, тире, неразрывные пробелы, переносы, выносные | внутренний стандарт |
| **Бренд-система «УЮТ»** | палитра, Cormorant/Manrope, характер иллюстраций | внутренний стандарт |
| **Правила проекта** (`README.md`) | без сборки, без inline-стилей в `index.html`, один `@media` на брейкпоинт, конвейер картинок и каталога | обязательный минимум |

**Целевой уровень:** WCAG 2.2 AA для всех страниц из области. Дополнительно приняты
2.5.5 (44×44) и 2.3.3 (reduced motion) как внутренние цели. При конфликте правил
приоритет: **доступность → сохранность контента → бренд → эстетика**. Например,
брендовое золото на кремовом фоне меняется на более тёмный оттенок, потому что
читаемость важнее точного hex.

**Что проверено, а что нет.** Текущий контур — Chromium через CDP, DPR 1 и 2, JS
включён и выключен, эмуляция `prefers-reduced-motion`. Реального Safari/iOS, Firefox,
VoiceOver/NVDA и мобильных устройств в контуре нет. Это **риск**, а не «проверено»:
до отдельного smoke-теста AA считается целевым уровнем, но не подтверждённым для
этих платформ. Сторонние iframe (Яндекс) оцениваются по контейнеру; их внутреннюю
верстку мы не контролируем.

**Поддерживаемые браузеры:** последние две стабильные версии Chrome, Safari
(macOS/iOS), Firefox и Edge. Пока матрица не проверена на реальных устройствах,
это цель, а не подтверждённый результат.

## 2. Принципы оценки

1. **Дефект — это измеримое нарушение реестра.** Обрезка, переполнение, контраст
   ниже порога, несовпадение краёв, недоступная кнопка. Субъективные вещи идут в
   «Рекомендация» с обоснованием, а не в дефекты.
2. **Замечание без доказательства не принимается.** В описании — ID правила,
   селектор, ширина вьюпорта, число (px, контраст, количество элементов) или
   ссылка на стандарт.
3. **Важность — по влиянию на пользователя и сценарий**, а не по заметности для
   дизайнера. Ошибка в записи, телефоне или форме важнее опечатки в футере.
4. **Трудоёмкость не понижает важность.** Дорогая правка остаётся в своей группе;
   трудоёмкость влияет только на порядок внутри группы.
5. **Осознанное исключение — не дефект**, если оно записано в §5 с причиной,
   владельцем и датой пересмотра.
6. **Проверять на реальных ширинах и в браузере**, а не по коду. CSS может
   выглядеть правильно и обрезать изображение в конкретном контейнере.

## 3. Как определяется важность

Важность не выбирается «на глаз»: она следует из типа правила и последствия.
В реестре указана базовая важность; по признакам ниже она может быть **повышена**
(например, дефект в главном сценарии), но для A/AA — не может быть понижена.
Для правил уровня A/AA важность **всегда** «Обязательно», независимо от того,
сколько элементов затронуто.

### Обязательно

Хотя бы один признак:

- нарушение WCAG 2.2 уровня A или AA;
- ломает главный сценарий: запись, отправка формы, телефон, выбор мастер-класса;
- теряется контент: обрезано фото, скрыт текст, не виден CTA;
- нет обходного пути для пользователя;
- видимый дефект на двух и более канонических ширинах из §6;
- ошибка, которую видит каждый посетитель (двойная нумерация, битая сетка).

### Важно

Хотя бы один признак:

- системная проблема, повторяющаяся в большинстве однотипных элементов (например,
  все карточки каталога, все пункты навигации); число затронутых элементов
  указывается в замечании;
- адаптивность на планшете или нестандартной ширине;
- консистентность дизайн-системы: CTA, радиусы, токены, состояния;
- конверсия под риском, но есть обход (форма скроллится — кнопка ниже);
- обещание в тексте не соответствует продукту (категории, «пробная живопись»);
- доступность не блокирует, но мешает: качество доступных имён сверх минимума,
  порядок объявлений, удобство навигации скринридером.

### Желательно

- полировка и гигиена кода без изменения сценария;
- читаемость юридических ссылок, форматы телефона, дубли текста;
- CSS-долг без видимого эффекта;
- улучшение, которое не меняет сценарий и не входит в A/AA.

### Рекомендация («Если будет время»)

- субъективная арт-дирекция (подбор фото, свет, кадрирование);
- нужны данные владельца или исследование (цены, ассортимент, IA);
- эксперименты без готового решения;
- критерий нельзя измерить или показать на скриншоте.

Это **не дефекты** и не основание блокировать правку. Если рекомендация становится
обязательной, она переносится в реестр §4 с измеримым критерием.

**Примеры калибровки:**

| Находка | ID правила | Группа | Почему |
|---|---|---|---|
| H1 распадается на 5 строк | TYP-07 | Обязательно | главный экран, 1051+ и 390, ломает композицию |
| Фото сертификата обрезано | ADP-02 | Обязательно | потеря контента на всех ширинах |
| «1. 1.» в описании | CNT-05 | Обязательно | видит каждый в сценарии записи; важность поднята по последствию |
| Золото на кремовом 1.6:1 | COL-01/COL-02 | Обязательно | нарушение AA |
| Форма: CTA ниже фолда | CMP-06 | Важно | конверсия, но есть скролл |
| Футер капсом, длинные названия | TYP-08 | Желательно | не блокирует, охват небольшой |
| Текст 8px (футер, служебные подписи) | TYP-02 | Важно | ниже минимума 11–12px |
| Подбор фотографий | — | Рекомендация | вкус/арт-дирекция, нет измеримого порога |

## 4. Реестр правил

Единственный нормативный список. Колонка «Источник» показывает, откуда взято
требование; «внутренний» означает проектное решение, а не цитату из WCAG.
Колонка «Проверка» — минимальный способ доказать нарушение или исправление.

### 4.1 Сетка и выравнивание

| ID | Правило и порог | Источник | Важность | Проверка |
|---|---|---|---|---|

**Формула контраста.** Относительная яркость по WCAG; сравнение — по неокруглённому
значению, в отчёте показывать два знака. Округление вниз — внутренняя конвенция,
а не требование WCAG. Для текста на изображении брать самый светлый/тёмный участок
под глифами.

распространяются на безопасность, юридические требования и данные пользователя.

## 6. Как проводится аудит

**Окружение:** локальный HTTP-сервер, Chromium через CDP (без npm-зависимостей),
DPR 1 и 2, JS включён и выключен, эмуляция `prefers-reduced-motion`.

**Канонические ширины (единственный список):**

- основные: `320 / 360 / 390 / 414 / 768 / 1024 / 1280 / 1440 / 1920`;
- границы брейкпоинтов: `359/361`, `379/381`, `649/651`, `699/701`, `899/901`, `1049/1051`.

`760` — историческая ширина старых скриншотов. В новых проверках и DoD
используется `768`; исторические измерения в `07`/`09`/`README` не переписываются.

**Скриншоты:**

- полный набор: `1920 / 1440 / 1280 / 1024 / 768 / 414 / 390 / 360 / 320`;
- минимум для любой правки: `1920 / 1280 / 768 / 390`;
- для адаптивной правки: добавить `320 / 360 / 414 / 1024 / 1440`;
- `css-matrix` — все канонические ширины и границы, два прогона одной версии = 0.

**Порядок:**

1. Скриншоты по набору выше.
2. Замеры: rects секций и ключевых блоков, распределение кеглей и цветов,
   `scrollWidth`, пересечения и обрезки.
3. Контраст: реальные пары «цвет текста / фактический фон», формула WCAG.
4. Клавиатура: TAB-порядок, фокус, диалоги, формы, фильтры; no-JS-прогон.
5. Код: `grep` по `!important`, мёртвым классам, дублям, инлайн-стилям; сверка с docs.
6. Каждое замечание — в формате §7, с ID правила и измерением.
7. Повторный прогон после правок: скриншоты + `css-matrix` + `test-*`.

**Команды:** см. [`tools/tests/README.md`](../tools/tests/README.md) и раздел
«Проверки после внедрения» в [`09-design-audit.md`](09-design-audit.md).

**Границы:** в текущем контуре нет реального Safari/Firefox, VoiceOver/NVDA и
мобильных устройств. Это фиксируется как риск, а не как «проверено». Сторонние
виджеты (Яндекс) оцениваются только по контейнеру — их внутреннюю верстку мы не
контролируем.

## 7. Как оформляется замечание

Каждый пункт содержит пять частей:

1. **ID правила** — из §4, например `A11Y-13`.
2. **Зачем** — проблема пользователя/бизнеса, а не «так красивее».
3. **Как сейчас** — селектор, ширина, измерение, скриншот; для контента — цитата.
4. **Как исправить** — конкретные шаги в терминах проекта (файлы, генераторы, тесты).
5. **Ожидаемый результат** — проверяемый критерий: «3 строки на 320–1920», «0 обрезанных
   пикселей», «контраст ≥4.5», «CTA видна без скролла на 390×844».

Запрещено: «некрасиво», «выглядит плохо», «надо переделать» без критерия. Если
проблема субъективная — она идёт в «Рекомендация» с пометкой «арт-дирекция/вкус».

## 8. Что не считается дефектом

- Осознанная редакционная асимметрия, если она повторяется и описана как приём.
- Брендовые цвета, если контраст проходит; отклонение hex без нарушения порога.
- Выбор фотографий, света и кадрирования — решение владельца/арт-директора, а не
  ошибка верстки.
- Внутренняя верстка сторонних iframe.
- Поведение, которое не воспроизводится ни в одном из поддерживаемых браузеров
  (матрица — в §1).
- Контентные решения (ассортимент, цены), если нет противоречия с обещанием на сайте.
- «Мне не нравится шрифт/оттенок» без измеримого критерия.

Осознанное исключение из правила фиксируется в §5 с причиной. Иначе оно вернётся
в следующий аудит как новый дефект.

## 9. Definition of Done для исправления

Пункт считается закрытым, когда:

1. **Правка внесена в проект**, не нарушает `README.md` и не увеличивает долг §10
   (baseline переснят, если долг уменьшился).
2. **Сняты измерения «до/после»** и подтверждён критерий из пункта; в замечании
   указан ID правила.
3. **Скриншоты** по набору §6: diff с baseline = 0 пикселей или отклонения
   перечислены и согласованы; контрольная пара одной версии = 0; `css-matrix` не даёт
   неожиданных расхождений.
4. **Тесты:** `test-lock`, `test-form`, `test-catalog`, `test-adapted`, `test-nojs`
   проходят. Для контраста и клавиатуры — `test-contrast`/`test-keyboard` или
   ручной протокол с таблицей «селектор / значение / порог»; для a11y — axe/Lighthouse,
   если доступен, иначе ручной протокол.
5. **Кэш:** для CSS/JS поднят `?v=` и проверен `grep`; для данных — пересобраны
   `catalog.js`/картинки.
6. **Доступность:** контраст пересчитан скриптом, клавиатурный сценарий пройден,
   фокус виден; для форм — сценарии ошибок и успеха.
7. **Документация:** пункт в `09` закрыт или перенесён, исключения §5 обновлены,
   baseline §10 обновлён, если изменился.

Если правка затрагивает юридические страницы, они проверяются по тем же правилам;
исключение CODE-01 не отменяет контраст, кегли, длину строки и фокус.

## 10. Baseline текущего долга

Замерено 23.11.2026 по `assets/css/styles.css` после правок по `09`; это точка
отсчёта по перечисленным показателям, а не норматив. Числа не «улучшают» отчёт:
они показывают, что новый код не должен добавлять долг. Исторический baseline
22.11.2026 (70 `!important`, 39 кеглей, 45 hex вне `:root`) — в `09` и коммитах.

| Показатель | Значение | Как померить |
|---|---:|---|
| `!important` | 0 | `grep -o '!important' assets/css/styles.css \| wc -l` |
| Уникальные `font-size` | 26 | `grep -o 'font-size:[^;}]*' ... \| sort -u \| wc -l` |
| Hex вне `:root` | 0 (всего 10) | `awk`/`grep` по файлу |
| `rgba()` | 36 | `grep -o 'rgba([^)]*)' ... \| wc -l` |
| Уникальные `border-radius` | 4 (`0`, `50%`, photo, pill) | `grep -o 'border-radius:[^;}]*' ... \| sort -u \| wc -l` |
| Уникальные `box-shadow` | 2 (`card`, `float`); ошибка поля — `outline`, не тень | `grep -o 'box-shadow:[^;}]*' ... \| sort -u \| wc -l` |
| Кастомные свойства `:root` | 24 | `grep -o -- '--[a-z0-9-]*:' ... \| sort -u \| wc -l` |
| Skip-link | есть | `grep -n 'skip-link' index.html` |
| `autocomplete` у полей | `name`, `tel`, `email` | `grep -o 'autocomplete="[^"]*"' index.html` |
| `aria-pressed` у фильтров | 6 | `grep -o 'aria-pressed' index.html \| wc -l` |
| `overflow-x:hidden` | нет; горизонтальный скролл 0 | `grep -n 'overflow-x' assets/css/styles.css` |

`09` — исторический снимок: его числа (например, «11 переменных в `:root`») могут
отставать от фактического состояния. Для DoD используется §10, а не числа из `09`.
